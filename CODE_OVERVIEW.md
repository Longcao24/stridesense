# CODE OVERVIEW

This repository = **a phone inertial-tracking demo** + **a StrideSense pitch deck (PPT) generator**.
Both parts share the same real recorded data (`uploads/`) and figures (`figs/`).

> For how to run it, see [HOW_TO_RUN.md](HOW_TO_RUN.md); for the demo's user/algorithm documentation, see [README.md](README.md).

---

## 1. Global Data Flow

```
            phone browser                         computer (python)
  ┌──────────────────────────┐
  │ index.html / index_en.html│  sensors→reconstruction→rendering
  │  deviceorientation/motion │
  │  ZUPT/PDR trajectory + gait│
  └────────────┬─────────────┘
               │ ⬆ upload (POST /upload)
               ▼
        serve_https.py  ───────────────►  uploads/upload_NNN.json
                                                   │
                                                   ▼ (make_figs*.py reads upload_005.json)
                                            figs/ , figs_en/  ── PNG figures
                                                   │
                                                   ▼ (make_pitch_tech_*.py references figures + video)
                                            *.pptx  ── pitch deck
```

Core idea: **the phone side is a self-contained web tool (zero dependencies)**; the computer side only does two things — **receiving uploads** + **offline generation of figures/PPT**.

## 3. Internal Structure of the Demo (`index.html`)

Single file, with logic partitioned as follows:

1. **Global state `S`**: orientation, rotation matrix, calibrated gravity, velocity/position, recording buffer, walking state `S.walk`, parameters `S.params`.
2. **Math**: `eulerToMatrix` (W3C ZXY intrinsic rotation → device→world rotation matrix), `matVec`.
3. **Permissions & startup**: `requestPermission` (iOS requires HTTPS + a user gesture) → registers the `deviceorientation` / `devicemotion` callbacks.
4. **Sensor callback `onMotion`**: rotates gravity-inclusive acceleration into the world frame → extracts linear acceleration (preferring iOS's fused `userAcceleration`, otherwise manually subtracting calibrated gravity).
5. **Two separate reconstruction modes (fully decoupled)**:
   - **Gesture mode**: causal preview while recording; after stopping, `reconstruct()` performs a **non-causal, boundary-constrained reconstruction** over the whole segment (smoothing → mean removal → integration → end-velocity = 0 detrending → position integration → optional loop closure).
   - **Walking mode PDR**: `walkStep()` does foot-strike detection (specific force ≈ g and small angular velocity) → integration during the swing phase → on foot strike, `commitStride()` settles one step (end-velocity = 0 drift removal + **vertical two-end constraint → re-anchor to the ground z=0 at every foot strike**, so vertical drift does not accumulate across steps), and collects gait quantities.
6. **Gait analysis**: `computeGait()` / `renderGait()` — stride frequency, stride time, CV, stance/swing, gait speed, stride length, foot-clearance height, foot tilt angle, turning, etc. (items not measurable from a single foot are grayed out).
7. **Render loop `renderLoop`**: the left Canvas draws the 3D phone orientation box; the right Canvas draws the 2D top-down view / 3D trajectory (rotatable by dragging).

## 4. Reconstruction Algorithm (the core in one sentence)

Position = double integration of acceleration, which inevitably drifts; we keep short gestures/individual steps under control via **world-frame gravity removal + high-pass bias removal + zero-velocity update (ZUPT) + velocity leakage**.
Walking can go far without drifting because **every foot strike is necessarily stationary → ZUPT zeroes out the drift on the spot**. For the detailed formulas, see the "Reconstruction Principles" section in [README.md](README.md).

## 5. Conventions and Dependencies

- **Coordinate system**: world frame, **Z up** (gravity-aligned, absolute); the X/Y heading is an arbitrary reference per session (no magnetometer, so yaw drifts slowly).
- **Color scheme / fonts**: a unified dark-theme palette; figures and PPT all use **PingFang SC** (Chinese and English, `①②③`, `ω`, `→`, `±`, etc. all render, with zero missing-font issues).
- **Dependencies**: the phone side has **zero dependencies** (pure browser APIs + Canvas); the computer side uses `python-pptx`, `numpy`, `matplotlib`; `serve_https.py` uses only the standard library + `openssl`.
- **Generation order**: change the demo → re-run `make_index_en.py`; change figures → first run `make_*fig*.py` / `make_figs*.py`, then run `make_pitch_tech_*.py`.
